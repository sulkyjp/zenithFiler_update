## Latest Changes — [1.14.4] - 2026-08-29 : Shortcuts during Japanese input, and keyboard operation in thumbnail views

### Changed

- **Scripts now accept a drop the same way executables do (#253):** Only **four kinds of file** could be launched by dropping onto them in the list: `.exe`, `.bat`, `.cmd` and `.com`. If your compression or conversion step happens to be a script — a `.jse` (encoded JScript), say — dropping onto its row was treated as **a copy or move into the folder you already had open**, which does nothing at all when the files were sitting in that folder to begin with. **`.js`, `.jse`, `.vbs`, `.vbe` and `.wsf` have been added**: Windows registers a drop target for each of them, so **Explorer runs them with arguments too**. The highlighted row, the changed cursor, the confirmation before launching and the choice of working folder are exactly as they are for an executable. `.ps1` and `.lnk` remain excluded — Windows itself passes no arguments to the former, and the latter may point at a folder, which makes it indistinguishable from a copy destination.

### Fixed

- **Fixed copy and paste shortcuts doing nothing while Japanese input is on (#259):** This started from a report that `Ctrl+C` and `Ctrl+V` did nothing in the feedback box. **The moment the input mode turns full-width, copy, paste, cut and select-all stop responding**; switching back to half-width brings them straight back. It was never limited to text fields either — **the shortcuts in the file list were dead in the same way** (selecting files and pressing `Ctrl+C`, say). While Japanese input is on, even a keystroke held down with `Ctrl` arrives as "a key the input method has already handled", and **the key actually pressed survives only somewhere else**. For a key in that shape neither the app's own shortcuts nor Windows' built-in copy and paste ever fire. The key actually pressed is now recovered before anything is matched against it, and copy, paste, cut, select-all, undo and redo in text fields are carried out explicitly. **The input method itself makes no difference** — it reproduced identically here with both Microsoft IME and Copilot Keyboard, and both are fixed. Typing mid-conversion is untouched: keystrokes without `Ctrl` are left exactly as they were, so conversion still behaves as before.

- **Fixed `Delete` and other keys doing nothing in thumbnail views (#261):** With a pane in small, medium or large icon (thumbnail) view, selecting a file and pressing `Delete` **deleted nothing and made the mouse pointer disappear instead** (moving the mouse brought it back). `Delete` was not alone: **arrow keys, `Enter` to open, `Backspace` to go up, `F5` to refresh and type-ahead search were equally dead** — every keystroke without a modifier was discarded while a thumbnail view was showing. The vanishing pointer was **the app deciding you had started working from the keyboard and hiding the cursor, while the key itself was thrown away a moment later**. The block dated from an early version, where it kept the thumbnail layout and the vertical scrolling from locking up as each waited on the other's size; **rebuilding that layout onto a fixed column count removed the reason**, and only the block was left behind. Thumbnail views now take the same keys as the list view. **`Left` and `Right` are the one exception**: the list view spends them on moving between panes A and B, but thumbnails are laid out across as well as down, so while you are in the file list they **move the selection sideways instead** (`Tab` or `F6` moves between panes). If you have assigned pane movement to some other key, that key still works in thumbnail views.

## 最新の変更履歴 — [1.14.4] - 2026-08-29 : 日本語入力中のショートカットと、サムネイル表示のキー操作を直した

### Changed

- **実行ファイルへのドロップを、スクリプトファイルでも受け付けるようにした (#253):** これまで一覧の中でドロップを受けて起動できるのは `.exe` / `.bat` / `.cmd` / `.com` **の 4 種類だけ**でした。圧縮や変換の処理を `.jse`（エンコード済みの JScript）のようなスクリプトで用意している場合、その行に落としても「**いま開いているフォルダへのコピー・移動**」として扱われ、同じフォルダの中で落としたときは結果的に何も起きません。**`.js` / `.jse` / `.vbs` / `.vbe` / `.wsf` を対象に加えました** — いずれも Windows 側にドロップの受け口が用意されていて、**エクスプローラー上でも引数付きで実行される**ものです。行の強調・カーソルの変化・起動前の確認・作業フォルダの決め方は、これまでの実行ファイルとまったく同じです。`.ps1` と `.lnk` は引き続き対象外です（前者は Windows のドラッグ＆ドロップでも引数が渡らず、後者はリンク先がフォルダのことがあり、コピー先と区別が付かないためです）。

### Fixed

- **日本語入力をオンにしていると、コピーや貼り付けのショートカットが効かなくなる問題を修正 (#259):** フィードバックの入力欄で `Ctrl+C` と `Ctrl+V` が働かない、という報告からたどり着いた問題です。**入力モードが全角になった瞬間から、コピー・貼り付け・切り取り・すべて選択が反応しなくなり**、半角に戻すと元どおり動きます。しかも入力欄だけの話ではなく、**一覧側のショートカットも同じように止まっていました**（ファイルを選んで `Ctrl+C`、など）。日本語入力をオンにしている間は、`Ctrl` を押しながらの打鍵まで「入力方式が処理済みのキー」としてアプリに届き、**実際に押されたキーが別の場所にしか残らない**のが原因です。この形のキーでは、アプリ独自のショートカットはもちろん、Windows 標準のコピー・貼り付けも動きません。実際に押されたキーを取り出してから照合するようにし、あわせて入力欄のコピー・貼り付け・切り取り・すべて選択・元に戻す・やり直しを肩代わりするようにしました。**入力方式の種類は問いません** — 手元では Microsoft IME でも Copilot Keyboard でも同じように再現し、どちらも直っています。**変換中の文字入力はこれまでどおり**です（`Ctrl` などを伴わない打鍵には手を触れていないので、変換の操作を奪いません）。

- **サムネイル表示のときに `Delete` などのキーが効かない問題を修正 (#261):** 小・中・大アイコン（サムネイル）で表示しているとき、ファイルを選んで `Delete` を押しても**削除されず、代わりにマウスカーソルだけが消える**状態でした（マウスを動かせば戻ります）。効かないのは `Delete` だけではなく、**矢印キーでの選択移動・`Enter` で開く・`Backspace` で親フォルダへ・`F5` での更新・頭文字を打っての絞り込みも同様**で、サムネイル表示のあいだは修飾キーを伴わない打鍵がひとつ残らず捨てられていました。カーソルが消えたのは、**キーボードで操作を始めたと判断してマウスカーソルを隠す動作だけが先に走り、肝心のキーはその直後に捨てられていた**ためです。これは初期のころ、サムネイルの並べ方と縦スクロールが互いのサイズを計算し合って固まるのを避けるための措置でしたが、**並べ方を固定列の方式に作り替えた時点でその必要はなくなって**おり、無効化だけが取り残されていました。サムネイル表示でも一覧ビューと同じキー操作ができます。**`←` `→` だけは扱いを変えました** — 一覧ビューでは A / B ペインの行き来に使いますが、サムネイルは横にも並ぶため、ファイル一覧に居るあいだは**選択の左右移動を優先**します（ペイン移動は `Tab` か `F6`）。ペイン移動へ `←` `→` 以外のキーを割り当てている場合は、サムネイル表示でもそのキーで移動できます。
