    How Index Search Works¶

    This article explains what index search does behind the scenes, from a user's point of view. If you only need to operate it and choose settings, Index Search and Index Settings are enough.

    Where the Index Lives¶

    The index is kept in data\index inside the app's folder. The registered folders and their lock state, the time of the last full rebuild, and the time of the last scheduled update are kept there too, so everything carries over when you close the app or restart the PC.

    What Gets Recorded¶

    For every file and folder under a registered folder, the index records its name, location (full path), size and date modified. File contents are not recorded. To search for text inside files, use file content search (grep) in the search bar (see Search).

    Name Matching¶

    Keywords are matched against the name (not the path; which folders are searched is decided by the search scope).

    • Japanese is split into words: "議事録" finds "第3回議事録.docx"
    • Partial matches are added: letters, digits and katakana that cannot be split into words are still found when they match part of a name
    • Spaces mean AND: results must contain every word. If nothing is found and the keyword contains a space, the search runs again automatically, matching any of the words (OR)
    • * and ?: work as wildcards (a leading one such as *report is allowed). The partial-match side treats them as literal characters, though, so to narrow reliably by extension use a regular expression as below
    • **Regular expressions (".*" on in the search bar)**: a .NET regular expression is applied to the name including its extension, keeping the original upper and lower case (for example \.xlsx$). If matching a single name takes more than 0.1 seconds, matching stops for the rest of that search, so an overly complex pattern cannot freeze it
    • Size and date filters: the size and date set in the search bar are applied while results are taken from the index

    Result Limits and Order¶

    • Index search takes up to 500 results, newest date modified first
    • Looking at a folder's contents with "Confirm index registration" on its right-click menu (no keyword) shows up to 1,000 items

    Normal Search vs. Index Search¶

    Item Normal search Index search
    Scope The current folder and everything under it The registered folders (those chosen in the search scope)
    What it reads Scans the disk on the spot The index (does not read the disk)
    Matching Partial name match and wildcards; regular expressions when ".*" is on As described in Name Matching
    Number of results No limit (added as they are found) 500
    How current Always the disk as it is now As of the last index update

    Normal search does not use the index. It can search folders you have not registered, but deeper folders take longer. Index search covers all registered folders together and returns results without reading the disk.

    How the Index Is Built¶

    • One folder at a time: only one indexing job runs at once; the rest wait their turn (their status shows "Waiting")
    • Box Drive is walked first: for Box Drive locations, the folders are opened once beforehand so Box prepares the actual files, which keeps them from being skipped as unreadable
    • Unreadable items are skipped: folders you have no access to, and items with the system or temporary attribute, are not read
    • Your work comes first: indexing runs at a lower priority and pauses briefly after writing each batch. The pause is shortest for local drives; with "Process network drives with lower priority" on it is longer for network and Box Drive locations, and "Update index in eco mode" lengthens it further
    • Recorded when done: the finish time and item count are saved, and the status shows "N items" (or "Complete")

    What Is Not Indexed (Exclusions)¶

    The following are skipped automatically even inside a registered folder.

    • Folder names: .git, .svn, .hg, node_modules, bower_components, .vs, obj, bin, .nuget, __pycache__, .mypy_cache, .pytest_cache, .tox, venv, .venv, .next, .nuxt, .gradle, $Recycle.Bin, System Volume Information, $WINDOWS.~BT, $WINDOWS.~WS, $WinREAgent, $SysReset, Recovery, PerfLogs, MSOCache, Config.Msi, INetCache, Temporary Internet Files, and every folder whose name starts with $
    • Locations: anything under AppData\Local\Temp (the temp folder) and under the internet caches (AppData\Local\Microsoft\Windows\INetCache, Temporary Internet Files)
    • File names: desktop.ini, Thumbs.db, ehthumbs.db, ehthumbs_vista.db, .DS_Store, .localized, .Spotlight-V100, .Trashes, NTUSER.DAT, ntuser.dat.LOG1, ntuser.dat.LOG2, ntuser.ini, UsrClass.dat, UsrClass.dat.LOG1, UsrClass.dat.LOG2
    • Other files: Office temporary files starting with ~$, files with the extension .tmp, .temp, .bak, .swp or .swo, and files with no extension

    How Changes Are Picked Up¶

    • The app's own operations are reflected at once: moves, copies, deletions and renames done in Zenith Filer are reflected in the index as soon as they finish, whatever the update mode. Records for places that are gone are removed along with everything under them, and new places are added along with everything under them (only under registered folders that are not locked). A batch rename's "A → temporary name → B" is applied in order. A folder with no record in the index shows its size as blank (unknown), not 0
    • Changes in open folders: when the update mode is "Auto-detect changes" or "Update at regular intervals", changes made outside the app to a folder open in a tab (creating, renaming, deleting, rewriting a file) are reflected too. With "Update only when needed" they are not. Changes in folders that are not open are not picked up this way
    • Scheduled updates: with "Update at regular intervals", registered folders are read again at the chosen interval. The last run time survives closing the app; if the interval has already passed when the app starts, the update runs 2 minutes after startup. For each folder, "Index Detailed Settings" lets you set the days, the time and the update mode
    • Incremental updates do not notice deletions: an incremental update ("Incremental update" on the right-click menu, and the default for scheduled updates) adds new and changed items only; records of files that have disappeared stay. To clean those up, use "Rebuild index", or set the folder's update mode to "Always full rebuild"

    Idle Execution (CPU load avoidance)¶

    You can keep scheduled updates from starting while the CPU is busy with other work.

    • Setting: in Control Deck → "Index", turn on "Update index only when CPU load is low" and pick the "CPU usage limit" below it (10% / 20% / 30%; 20% by default)
    • When it applies: before a scheduled update of "Update at regular intervals" starts. While CPU usage is above the limit, it measures again every 10 seconds and waits. Searching works as usual while it waits
    • Minimum interval between full rebuilds: choosing "Full rebuild" sooner than the "Minimum Full Re-index Interval" (6 / 12 / 24 hours; 24 hours by default) does nothing and tells you "Full rebuild was already executed within N hours"
